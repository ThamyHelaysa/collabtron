# One `steps` message for accepted and missing Steps

The sync protocol of [ADR 0001](0001-central-authority-over-crdt.md) (issue #10) has three server messages over the WebSocket at `/ws/<post-id>`: `init` (instance ID, Version, document), `steps` and `heartbeat`. Saving adds a fourth, `save` ([ADR 0006](0006-server-saves-never-over-outside-changes.md)), and Presence a fifth, `presence` ([ADR 0007](0007-presence-relayed-at-the-authority-version.md)). A `steps` message always means "these are the Steps from Version `version` on, with the Collaborator that made each". The Authority sends it in two cases: to every Collaborator of the Post when it accepts Steps, the sender included, and to the sender alone when its Steps were based on a stale Version. The client treats both the same way: it skips the Steps it already has, applies the rest with `prosemirror-collab`'s `receiveTransaction` (which confirms its own Steps and rebases the unconfirmed ones), then sends what is still unconfirmed.

## Considered Options

- **Separate `steps-accepted` and `steps-missing` messages**: rejected. The client would do the same thing for both, and a rejection often repeats Steps the broadcast already delivered, so the client needs the skip-by-Version logic anyway.
- **Rejecting with no Steps, since the broadcast delivers them**: rejected. Reconnecting clients will not have been there for the broadcast ([ADR 0008](0008-reconnect-catches-up-or-offers-the-text-back.md)).

## Consequences

- A client sends one batch at a time and waits for its answer before the next: a `steps` message with its own Steps (accepted), or one with nothing new (rejected). A rejection never brings news to a connected client, because the Steps it missed were broadcast when they were accepted, before the Authority got to its batch. A client back from a dropped connection was not there for the broadcast: it recognises the answer by its `version` instead, and sends its rebased batch as soon as the batch that beat its own arrives, without waiting for the rejection ([ADR 0008](0008-reconnect-catches-up-or-offers-the-text-back.md)).
- A message that is not valid (a Step that does not apply, a Version the Authority never had, no Steps, Steps that remove the Front Matter Block) closes the socket; none of its Steps are accepted. A correct client never sends one. The Front Matter Block rule is checked by the Authority too, because a client refuses such a transaction and would stop following the Post.
- An Authority is loaded from the Post file when the first Collaborator joins and dropped when the last one leaves, Step log included. Its instance ID goes with it ([ADR 0008](0008-reconnect-catches-up-or-offers-the-text-back.md)). The next Collaborator reads the Post file again, so changes made to the file with nobody connected are picked up. What is pending is saved first ([ADR 0006](0006-server-saves-never-over-outside-changes.md)).
- `clientID` is taken as sent. A client that lies about it can make another Collaborator drop unconfirmed Steps; this needs the token handshake first, not a fix here.
- There is no auth yet, and browsers let any site open a WebSocket to localhost, so the upgrade is refused when `Origin` is not the editor's own page. Clients that send no `Origin` (tests, scripts) are let in. This check goes away only when the token handshake replaces it.
- Saving is the Server's alone, from the Authority's document: the Save button and its `PUT` are gone ([ADR 0006](0006-server-saves-never-over-outside-changes.md)).
- New dependencies: `ws`, because Node has a WebSocket client but no server; `prosemirror-collab`, chosen in ADR 0001; `prosemirror-transform`, already installed through the other ProseMirror packages, now declared because the Authority and the client import `Step` from it.
